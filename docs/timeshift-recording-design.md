# 手動タイムシフト録画の組み込み設計

状態: 初期実装を追加（2026-09-09）。アプリでの認証付き実番組確認を進めている。以下は受け入れ条件と実装の対応をまとめたもの。[検証結果と初期対応範囲](timeshift-feasibility.md) を前提に、変更箇所・動作・受け入れ条件を具体化する。検証スクリプトは比較・再現用に残す。

## 利用者から見た動作

手動録画欄へ終了済み番組の ID または視聴 URL を入力すると、アプリでログイン中のアカウントを使って、先頭から取得する。ライブかタイムシフトかを選ぶ操作は追加しない。放送中なら従来のライブ録画、終了済みならタイムシフトとして開始する。

- タイムシフトは5並列＋先読みで取得する。並列数の設定UIは追加しない。
- 録画カードに「タイムシフト」と取得進捗を表示する。表示する経過時間はダウンロードの実時間であり、番組の再生時間と混同させない。
- 動画とコメントがそれぞれ終わるまで録画ジョブを保持する。コメントだけの失敗なら動画は継続し、最終結果を「一部失敗」とする。
- 手動停止は「停止」として履歴へ残す。全編の「完了」として表示しない。取得済みの部分ファイルは残す。
- 再実行は途中位置からの再開ではなく、先頭からの再取得とする。既存動画・コメントを上書きしない。
- 自動検知は従来どおりライブが対象。自動録画の終了後にタイムシフトを取得し直す動作は追加しない。

## 既存の自動録画を維持する条件

既存の自動録画の動作を変えないことを受け入れ条件とする。タイムシフト用処理を別ファイルに置くことだけでは十分ではなく、共通の開始管理・履歴・停止処理でも以下を守る。

- タイムシフトへの分岐は `source === 'manual'` かつ取得した番組情報が ended の場合に限定する。push / poll は必ず従来のライブ経路へ渡し、ended なら従来どおり終了する。
- pushの購読、ポーリング周期、録画対象の有効判定、起動時の放送中番組の扱い、既知番組管理、手動停止後の自動再開抑止を変更しない。
- 自動検知の `handleDetected` は現在、開始エラーの末尾が `ended` かを見て再試行を打ち切る。この契約を維持し、タイムシフト向けの視聴不可エラーへ一括置換しない。自動録画の開始再試行・既知状態の解除が変わらないことを確認する。
- ライブのHLS取得、視聴接続の再接続、403時の認証更新、異常終了後の別パート再開、コメントCSV追記を維持する。タイムシフトの5並列・有限履歴・新規CSV・完了判定をライブへ適用しない。
- 新しいモード・完了区分・進捗の未指定値は従来動作とする。旧履歴・ライブ履歴のコメント件数、保存先、ファイル参照、表示・絞り込みの意味を変えない。タイムシフトだけで使うフィールドの意味を共通処理に漏らさない。
- タイムシフトの失敗・キャンセルで、自動録画のcontroller、ソケット、FFmpegを停止しない。同じ番組の二重開始は引き続き防ぐ。ログアウト・アプリ終了で全録画を止める既存の動作は維持する。

通信帯域・CPU・ディスクは同時実行時に共有される。別経路にしただけで負荷の影響までゼロと断定せず、自動録画とタイムシフトを同時に動かした確認を行う。先読み・キャッシュの上限、進捗通知の間引き、停止可能なコメント保存処理で負荷を制限する。自動録画の取りこぼしや検知遅延が確認された場合は、タイムシフト側の負荷制御を見直し、自動録画の品質・再開動作を緩めて対処しない。

### 必須の回帰確認

| ケース                                         | 維持する結果                                                             |
| ---------------------------------------------- | ------------------------------------------------------------------------ |
| push / poll から放送中の対象を検知             | 従来のライブ録画が始まる。タイムシフト専用関数は呼ばれない               |
| 自動検知後の情報取得で ended                   | タイムシフトを始めず、不要な開始再試行も増えない                         |
| 対象無効、起動時録画OFF、手動停止済み          | 従来の条件で自動録画を抑止する                                           |
| ライブの一時切断、403、出力ファイル消失        | 既存の再接続・認証更新・別パート再開とCSV追記を維持する                  |
| ライブ録画とタイムシフトの同時開始・停止・失敗 | 片方の停止・失敗が他方を中止せず、別々に結果を確定する                   |
| 同時稼働中に新しい放送を自動検知               | 対象の録画開始がタイムシフトの完了待ちにならない                         |
| 旧履歴・ライブ履歴とタイムシフト履歴が混在     | 旧項目の参照・件数・状態・絞り込みを維持し、既存ファイルへ重複追記しない |
| ログアウト・アプリ終了                         | 全ジョブの停止・保存・後始末を既存の終了管理へ参加させる                 |

分岐・停止の独立性・保存互換性は偽サーバーやモックで確認する。帯域・ディスク負荷を含む同時稼働は隔離したアプリ環境で確認する。既存テストの通過だけをもって、実装後の自動録画への無影響を確認済みとはしない。

## モードと開始判定

`RecordingMode = 'live' | 'timeshift'` を設け、`RecordingInfo` と `ProgramRecorderOptions` に渡す。本体の呼び出し側は明示し、既存のCLI・旧履歴で未指定なら live とする。`source` は引き続き manual / push / poll を表し、モードとは別に保持する。

| 開始元・番組状態                   | 動作                                                   |
| ---------------------------------- | ------------------------------------------------------ |
| manual / onAir                     | live を開始                                            |
| manual / ended / WebSocket URLあり | timeshift として視聴接続を試す                         |
| manual / ended / WebSocket URLなし | 視聴不可を返す。会員種別や予約不足だと断定しない       |
| push・poll / ended                 | 従来どおり録画しない                                   |
| released・unknown                  | タイムシフトには切り替えず、ライブの従来判定を維持する |

番組情報を取得した時点でモードを固定する。ライブとして開始した処理を、途中で ended になったことだけでタイムシフトへ切り替えない。取得開始前の二重起動抑止、ログアウト・終了中の開始取消、保存先選択は既存の管理を使う。

視聴不可用の固定エラーコードを追加し、「このアカウントではタイムシフトの視聴接続情報を取得できませんでした。公式サイトでの視聴可否とログイン状態を確認してください」と表示する。番組情報自体の取得失敗と分ける。既存の汎用エラーからは「終了済みだから取得不可」という文言を除く。

## タイムシフト用の処理構成

以下の役割を専用モジュールに分ける。`src/` から `scripts/` を import せず、検証で確認した処理を製品用の型・エラー・ログ・保存管理に合わせて移す。

| 追加する役割・ファイル案                                     | 責務                                                                                    |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `core/recorder/timeshift-program-recorder.ts`                | 1本の視聴接続を管理し、動画とコメントを開始・回収して結果をまとめる                     |
| `core/nico/timeshift-session.ts`                             | 接続情報の受信、ping / keepSeat、期限付き待機、終了処理。検証の `session.ts` を基にする |
| `core/nico/timeshift-playlist.ts`、`timeshift-download.ts`   | 元のENDLIST確認、タグ検証、固定したプレイリストの5並列取得・復号・順序付き出力          |
| `core/recorder/timeshift-video-recorder.ts`                  | プレイリスト選択とFFmpeg、動画の完了・欠落判定、進捗通知                                |
| `core/recorder/timeshift-comment-recorder.ts`                | View入口探索、過去履歴・直近分の巡回、重複除去、終端・上限の判定                        |
| `timeshift-comment-recorder.ts` の `convertTimeshiftComment` | protobuf のチャットからCSV用 `NicoComment` とソートキーへの変換                         |
| `core/recorder/timeshift-comment-recorder.ts`                | 取得中の部分保存、ソート、既存14列CSVへの出力、コメントの結果                           |

低水準のHLS解析・Cookie処理・FFmpeg・protobufローダーは既存のものを再利用する。検証用のJSONレポートやCLI上限を、そのまま製品全体のインターフェースにはしない。巨大な共通レコーダーへの統合や vendor の構造変更は今回行わない。

### 視聴セッションと終了順序

1. HLS・messageServer・失敗のリスナーを接続前に登録し、早い応答の取りこぼしを防ぐ。接続・接続情報待ちはそれぞれ期限を持つ（初期値15秒）。
2. HLSが得られたら動画を開始する。messageServerの情報は同じ接続から取得し、15秒以内に来なければコメントだけ失敗として動画を続ける。
3. 動画とコメントの取得中は ping / keepSeat に応答する。再接続要求、予期しない切断、明示的な視聴拒否は、未完了の取得を失敗として停止する。初期対応ではセッション・URLの再取得は行わない。
4. END_PROGRAM は取得完了の根拠にしない。終了通知だけなら現在の有限取得を続け、実際に接続を失った場合は未完了を完了にしない。
5. 動画の正常終了ではコメントを中止しない。コメントの正常終了・失敗でも動画は止めない。動画失敗時はコメントを停止し、部分結果を残す。
6. 両方の終了・部分結果の保存を待ち、セッションとタイマー、FFmpegを回収してから履歴を確定する。既に完了した成果物の結果は、後から起きた他方の失敗で取り消さない。

外側の停止要求と内部失敗による abort を区別する。映像のHTTPエラーでコメントを中止したケースを「ユーザーが停止した」と記録しない。サーバー自由文・Cookie・署名付きURLはログやメタデータに保存せず、固定コードとHTTPステータスを使う。

### 動画の取得・完了判定

- 最高帯域の映像と対応する音声を選び、元の両プレイリストにENDLISTがあることを確認する。全編では合成ENDLISTを根拠にしない。
- 検証で確認した各トラック5並列・先読み5件＋出力中1件を採用。鍵・初期化情報のキャッシュにも件数制限を設ける。1リソース32MiBを初期上限とし、超過を明示的な失敗にする。
- blankを除く保存予定数を先に確定する。先頭・末尾の空白と本編の境界は許可する。本編同士のDISCONTINUITYは、復号後のfMP4の初期化情報が同一で、全トラックのDTSが境界前後で連続するときだけ許可する。境界に接するセグメントのみ解析し、先頭映像や音声の開始時刻を変更しない。時刻の巻き戻り・空白、形式変更、解析できない形式は次のセグメントをFFmpegへ流す前に拒否する。
- 本編途中にblankを挟む不連続、BYTERANGE、GAPなどは引き続き未対応とする。プレイリストのタグ数・境界位置・前後がblankか本編かをログとJSONに残す。URI・Cookie・属性値は診断へ含めない。
- 元のセグメント番号、鍵・初期化情報の切り替え、明示IV・暗黙IVを維持する。受信順が前後しても元の順で出力する。
- メディア・鍵・初期化情報の取得はヘッダー待ち20秒、本文の無通信時間20秒を上限とする。受信が進んでいれば総時間20秒を超えても継続する。プレイリストは1要求20秒。両方とも一時的な通信エラー・408・429・5xxだけ最大4試行し、待機中も停止できる。403は失敗、セグメントの404は欠落数を残す。鍵・初期化情報の404は失敗。
- 404欠落は両トラックの取得後に判定する。停止や失敗でも入力パイプを閉じ、FFmpegが取得済みデータを排出するのを最大15秒待つ。期限までに閉じなければ終了を要求し、完了扱いにはしない。
- 全トラックが終端まで処理され、保存実績が予定と一致し、欠落0・保存数1以上・FFmpeg終了コード0の場合のみ動画の取得完了とする。ファイルが消失していた場合も完了にしない。
- `ended` だから成功とする再開ループには入れない。失敗後の先頭からの取り直しは利用者が手動開始する。

進捗は両トラックの保存済みセグメント数 / 保存予定セグメント数をまとめて通知する。受信しただけの先読みデータは進捗に含めない。動画100%でもコメント取得・ファイル確定が残る間はジョブ完了にしない。通知頻度は既存の状態通知に合わせて間引き、セグメントごとに画面更新・履歴書き込みを行わない。

### コメントの取得・保存

Viewは `at=now` から開始し、nextしかなければそのカーソルを辿る。データの入口が見つかったViewをnextまで読み、backwardの終端とそこで提供されたprevious / segmentを読み切る。以後の新規コメントを待つ継続ポーリングは行わない。

Viewの応答待ちは1要求60秒を上限とし、通常のファイル取得の20秒とは分ける。待機上限に達したときは `COMMENT_VIEW_TIMEOUT` として部分保存する。各View要求の応答待ち時間と受信エントリー数をJSONへ残す。URL・カーソル値は診断に含めない。

- 保存範囲の結果は `status: complete | partial` と `reason`・`aborted` で記録し、全コメントの完全性とは区別する。nextのみ・循環・上限・途中フレームの欠落を正常な空履歴とみなさない。
- 初期の内部上限は検証済みの20万件・受信128MiB・履歴2000ページ・入口探索3回を採用する。コメント取得時間は30分を上限とし、動画にはこの全体時間制限を適用しない。上限到達時は取得済みを保存して一部失敗を表示する。将来の上限変更は実データの規模を見て判断する。
- 検証の最小JSONLと異なり、投稿者・装飾など既存CSVの14列を埋める。既存 `NicoComment` の値表現に合わせた専用変換を作り、通常チャット・overflowed_chat・装飾省略をテストする。vendor の private メソッドを外側から呼び出さない。
- IDで重複除去する。IDがない場合は元の投稿時刻（秒・ナノ秒）、番組、コメント番号、本文を使い、欠けたIDだけを理由に別コメントをまとめない。
- 投稿時刻（秒・ナノ秒）→コメント番号→取得順で安定ソートする。CSVの `at` は既存どおり日本時間のミリ秒精度、vposは受信値を保持する。冒頭blankの分だけvposを補正する処理は、対応が確認できていないため追加しない。
- 装飾の省略には既定値を使うが、投稿時刻など必須値が不正なチャットを現在時刻で補完しない。不正な投稿時刻の1件だけを除外して後続を取得し、不正件数を残して完全取得扱いしない。通信・保存エラーまで読み飛ばさない。チャット以外の制御メッセージは通常の除外として扱う。

取得中は新しいCSVへ取得順で部分保存し、上限内のソート情報を保持する。取得の終了時には、同じディレクトリの新規一時ファイルへソート済みCSVを書いてから、その実行で作ったCSVだけを置き換える。複数行の本文を壊さないよう、CSVを行単位で分割してソートしない。BOM・ヘッダー・引用符処理は既存のCSV変換を再利用する。

メモリ内の件数・シリアライズ済みデータ量にも上限を設ける。ソート・ファイル確定中もキャンセル可能な単位で処理する。停止要求が来たらソートを打ち切り、速やかに後始末する。停止・強制終了・保存先障害では取得順の部分CSVが残るため、メタデータに `sorted` と部分取得状態を残す。置換失敗時も元の部分CSVを消さない。

## 保存先・再取得・履歴の互換性

配信者フォルダ、放送開始日時によるファイル名、TS・CSV・メタデータJSONという構成は維持する。ただしタイムシフトは再実行ごとに新しい連番の動画・CSV・JSONを一組作り、既存CSVへ全履歴を追記しない。

現状の `resolveAvailableAttempt` はTSの存在しか見ないため、タイムシフト用の組の予約ではCSV・JSON・作成中の一時ファイルも衝突判定に含め、排他的に確保する。過去の取得で動画を作る前に失敗した場合やCSVだけ残っている場合も上書きしない。確保した未完成ファイルの扱いはその実行の管理下で行う。

履歴は現在と同じ番組ID単位の1件を維持する。

- `videoPaths` は過去の実在動画を引き継ぎ、新しい動画を追加する。`videoBytes` は従来の累計を維持し、今回の進捗とは別にする。
- 新しい任意フィールド `commentsPaths` に過去の実在CSVと今回のCSVを保持し、`commentsPath` は最新のCSVを指す。履歴のコンテキストメニューから過去CSVも開けるようにする。
- `commentCount` は最新CSVの件数とし、過去の再取得分を足さない。今回のCSVを作るまでは過去の参照・件数を維持し、新規CSV確保時に最新参照と件数を切り替える。
- `attempt` は空き連番であり、タイムシフトでは「再開N回目」ではなく「取得N回目」と表示する。途中位置から再開したように見せない。
- `mode` など新規フィールドを持たない旧履歴は従来の意味で読む。旧JSONLは変換・追記・削除せず、タイムシフトでは新しいCSVを作る。
- 本体実装時に [出力ファイル仕様](files.md) を実装に合わせて更新する。初期実装とともに更新済み。

## 状態と結果の扱い

`RecordingState` の既存5状態は維持し、タイムシフト用の任意フィールドとして `completion: 'complete' | 'partial' | 'cancelled'`、動画進捗、コメント状態を追加する。これはUI・メタデータに必要な情報の案であり、型の具体的な入れ子は実装時に合わせる。

| 条件                                   | 履歴の状態・結果             | 表示                                                       |
| -------------------------------------- | ---------------------------- | ---------------------------------------------------------- |
| 開始・接続情報待ち                     | starting                     | タイムシフト・開始中                                       |
| 動画またはコメントの取得中             | recording                    | 動画取得率、コメント件数。動画完了後はコメント取得中と表示 |
| ソート・メタデータ確定                 | finishing                    | 保存処理中                                                 |
| 外側から停止要求                       | finishing → done / cancelled | 停止中 → 停止。全編完了とは区別                            |
| 動画完了・コメント履歴を読了           | done / complete              | 完了（提供された範囲の取得結果）                           |
| 動画完了・コメント未完了または失敗     | done / partial、errorあり    | 一部失敗。コメントの原因を表示                             |
| 動画失敗・欠落・出力消失               | failed / partial、errorあり  | 中断。終了済み番組でも成功へ変換しない                     |
| 異常終了したジョブをアプリ起動時に復元 | failed / partial             | 中断                                                       |

既存の `StateBadge` は error / state / ファイル存在から表示を決めるため、タイムシフトの cancelled を完了表示より先に評価する。`finishing` も現在は手動停止と同義の表示なので、保存処理中と停止要求中を区別する。履歴の「完了」フィルタはタイムシフトの cancelled を除外し、「停止」で絞れるようにする。ライブの既存状態・表示を一括変更しない。

メタデータにはモード、今回の各トラックの予定・実績・欠落・停止理由、コメントの範囲・ソート状態、固定エラーコード、取得の実時間を追加する。`program` 全体をそのまま保存すると WebSocket URL が含まれ得るため、タイムシフト用の番組メタデータは公開情報を選んで保存する。内部の接続データを履歴へ混ぜない。
