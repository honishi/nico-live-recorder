# 開発者向けドキュメント

nico-live-recorder の仕組み、開発の手順、コード構成、リリースの流れをまとめています。
作業の規約 (ブランチ、コミット、テストの方針) は [AGENTS.md](../AGENTS.md)、出力するファイルの一覧は [files.md](files.md) を参照してください。

## 仕組み

```
放送開始の検知
  ├─ Web Push (Mozilla AutoPush 経由、ニコニコの push 通知を購読)   ... 主
  └─ フォロー中番組 API のポーリング (既定 30 秒)                    ... 副 (取りこぼし防止)
        ↓ 対象配信者の放送なら
録画
  ├─ 視聴 WebSocket (startWatching) → HLS の URI と cookie を取得
  ├─ 映像・音声の playlist を追跡し、セグメントを取得して AES-128 を復号
  ├─ ffmpeg にパイプで渡し、再エンコードせず 1 本の .ts に多重化
  └─ NDGR からコメントを受信し .comments.csv に追記
```

- push 通知は **ログイン中のアカウントがフォローしている配信者** の放送開始にだけ届きます。アプリはフォロー状態の確認だけを行い、フォロー操作はしません。
- 未ログイン、または有効な録画対象が 0 件のときは、ポーリングも push の接続も止めます。パッケージ版の更新確認やユーザー操作による通信は別に行います。
- 映像と音声が別 playlist の場合は ffmpeg の fd3 / fd4 に渡します。音声込みの playlist では fd3 だけを使います。master playlist の中で帯域が最大の映像を選びます。
- HLS を ffmpeg に直接渡さないのは、ニコニコが同名の CloudFront cookie をパス別に複数配るためです (ffmpeg の cookie 管理は名前単位で、正しく送れません)。
- ライブ録画の playlist の再取得は RFC 8216 の下限 (変化ありなら target duration、なしならその半分) を守ります。視聴 WebSocket の再接続は録画ごとに 1 本だけ動かし、試行回数も録画全体で数えます。
- ライブ録画の映像が途中で止まったら、放送終了や視聴接続情報の有無を確認して、連番付きの別ファイル (`_2.ts`, `_3.ts`, …) で再開を試みます。開始を含め最大 10 回、待機は 5 秒から倍増して最大 60 秒です。録画中に出力ファイルが消されたことも検知して、別ファイルで再開します。これらの再開判断は `RecordingManager` が行います。
- ライブ録画では、コメント保存の失敗だけなら映像録画を続けます。映像が異常終了した場合はコメント取得もいったん止め、再開時に同じ CSV への追記を再開します。アプリは新しいCSVを使うときだけ取得可能な過去コメントも取得します。
- 手動停止した番組はアプリの実行中は再検知しても録画しません。手動録画で再開できます。録画中は OS の自動スリープを抑止し、終了時は録画の停止とログの書き出しを待ちます (それぞれ最大 15 秒 / 2 秒)。
- ライブコメントのView要求は開始間隔を最低1秒あけ、取得位置の停滞・後退時は最大30秒まで延ばします。停滞が10回以上かつ10分以上回復しない場合のみ、コメント取得をエラー終了し、自動再接続しません。取得位置が前進すれば待機・異常カウントを戻します。投稿件数は判定に使わず、位置が進む無コメントの放送は監視を続けます。
- ライブコメントの次の取得位置（next）が欠落した場合は、番組ページ・視聴接続情報の再取得前に1秒から最大30秒まで待機します。欠落が10回以上かつ10分以上回復しない場合のみコメント取得を打ち切ります。取得位置の前進を確認した場合だけ欠落カウントを戻し、欠落と古いnextが交互に返っても無制限に再接続しません。打ち切り後も保存済みCSVを残し、映像録画は継続します。
- 放送検知の実装は [chrome-nico-alert](https://github.com/honishi/chrome-nico-alert)、コメント取得は stream-journal の nico-client を元にしています。

タイムシフトは各トラック5並列で先頭から取得し、提供された過去コメントを有限巡回して時刻順のCSVへ保存します。ライブ向け再接続・別パート再開は適用しません。動画100%でもコメント取得が残ればジョブを保持し、停止・一部失敗を全件取得完了と区別します。全セグメントの取得試行とFFmpegの正常終了後に判明する `SEGMENTS_INCOMPLETE` では、コメント取得を継続して動画の欠落を部分結果に残します。それ以外の映像障害は未完了のコメント取得も止めます。再実行は新しい連番のTS・CSV・JSONを一組作ります。

## 開発

Node のバージョンは `.node-version` に固定しています (nodenv などで自動的に切り替わります)。
Electron 44 が内蔵する Node と同じ 24 系で、`min-release-age` などに使う npm 11 が同梱されます。

```bash
npm ci
npm run ffmpeg:build # 録画用 FFmpeg をビルド (前提ツールは下記参照)
npm run dev          # electron-vite の開発モードで起動
npm run format       # prettier
npm run lint         # eslint (型情報を使うルールを含む)
npm run typecheck
npm test             # vitest
npm run build        # out/ に成果物を出力
```

Electron を起動せずに録画部分だけを試すスクリプトもあります。

```bash
npx tsx scripts/record.ts lv123456789 30 ./recordings      # 30 秒だけ録画
npx tsx scripts/record-comments.ts                          # コメント取得のみ
NICO_USER_SESSION=... npx tsx scripts/push-listen.ts        # push 購読の疎通確認
npm run build && npx tsx scripts/e2e-screenshots.ts ./.cache/screenshots # macOS で各タブの撮影と実放送の手動録画確認
```

スクリプトはリポジトリ直下で実行します。`record.ts` はライブ録画専用で、終了済み番組をタイムシフトへ自動切り替えしません。録画秒数を省略すると番組終了または Ctrl-C まで動作し、アプリ側の別ファイルへの自動再開は行いません。ログインが必要な放送には `NICO_USER_SESSION` で `user_session` Cookie を渡せます。`record-comments.ts` もライブ用で、既定で直近の放送から 1 件を選び、30 秒取得します。このスクリプトは `NICO_USER_SESSION` を読み込まず、匿名で接続します。`push-listen.ts` は push とフォロー中番組のポーリングを確認し、録画は行いません。

検証用に起動するときは、必ず `NLR_USER_DATA` (設定の置き場所) と `NLR_OUTPUT_DIR` (保存先の既定値) を一時ディレクトリにして、本番の設定や録画に触らないようにしてください。`NLR_OUTPUT_DIR` は保存済みの設定を上書きしないため、未使用の userData を指定します。`e2e-screenshots.ts` は出力先の下に両方を設定し、CDP のポート 9334 を使います。撮影に加えて実放送を取得し、約 12 秒の録画も行います。

```bash
# macOS / Linux のシェル
nlr_check_dir=$(mktemp -d)
NLR_USER_DATA="$nlr_check_dir/userdata" NLR_OUTPUT_DIR="$nlr_check_dir/recordings" npm run dev
```

失敗後の再開処理は `NLR_DEV_FAIL_VIDEO_AFTER_MS=8000` のように設定して起動すると、映像を強制的に失敗させて確認できます。

終了済み放送の検証スクリプトについては [タイムシフト検証手順](timeshift-probe.md)、検証の結論と本体実装へ引き継ぐ範囲は [検証結果と初期対応範囲](timeshift-feasibility.md) を参照してください。 本体への変更方針は [手動タイムシフト録画の組み込み設計](timeshift-recording-design.md) にまとめています。手動入力した終了済み番組は専用の有限取得へ分岐し、自動検知と放送中の手動録画は従来のライブ経路を使います。

### UI の更新通知

アプリ状態・ログ・設定は別の IPC で配信します。`app-status.ts` が状態とログの取得を担当し、`ui-updates.ts` が変更イベントを配信へ結び付けます。

- AutoPush の接続・切断・購読修復状態は `onStateChanged` → `WebPushManager` の `status` → `RecordingManager` の `change` で伝えます。最終受信時刻も `status` で通知します。接続済みの判定は従来どおり WebSocket の開通で、HELLO の完了とは区別します。
- 録画の開始・終了・進捗・ファイル名確定・コメント件数は `change` で通知します。認証・設定・更新確認にもそれぞれ変更通知があります。ログを削除・抑制しても状態更新は届きます。
- `app:statusChanged` はアプリ状態、`app:logsChanged` は表示対象のログ、`app:settingsChanged` は設定の再取得通知です。初期取得は `getStatus()`・`getLogs()`・`getSettings()` を使います。`AppStatus` にログは含めません。
- ログの `entry` はログ配信だけを予約します。debug 非表示時の debug は配信せず、表示切り替え時に保持済みのログを載せ直します。ログのリングバッファ・ファイル出力・未読件数の扱いは維持します。
- 各配信は200ms単位でまとめます。取得を並列に走らせず、取得結果を順に配信します。取得中に変更があれば配信後に取り直すため、変更が連続しても配信が止まりません。Renderer は受信済みの通知を遅れた初期応答で上書きしません。設定の再取得は設定通知からだけ行います。
- 保存先の書き込み可否と直近の録画ファイルの外部削除は、ウィンドウがフォーカスされたときと、表示中の30秒ごとの確認で反映します。履歴タブは従来どおりタブを開いたときや履歴変更時に再取得します。

AutoPush の `onStateChanged` と状態変化の通知、および停止時の購読解除は流用コードへの独自追加です。上流の変更を取り込む際も、ログ出力と独立した通知を維持してください。

### 流用コードの独自変更

stream-journal 由来の `vendor/nico-client/` には、このアプリで追加した独自変更があります。`NicoClient.ts` の `streamComments` にあるView要求の最小間隔、取得位置の停滞・後退・next欠落に対するバックオフと打ち切り、回復待ち中の一度だけの警告、および `errors.ts` の `CommentViewStalledError` / `CommentViewMarkerMissingError` が該当します。流用元の更新を取り込む際は、これらの保護を保持するか同等の処理へ置き換え、`test/vendor/nico-client/NicoClient.test.ts` と `test/core/recorder/comment-recorder.test.ts` で正常な受信・回復・停止・要求回数の上限を確認してください。この記載は独自変更の所在を示すもので、流用元の最新コードへの反映状況は確認していません。

### 録画の共通部品

ファイル名生成は `core/recorder/recording-paths.ts`、CSV変換は `comment-csv.ts`、ライブ・タイムシフト間の共有型は `recording-types.ts` に置きます。タイムシフトからライブのレコーダー実装を経由せず参照します。`src/`・`test/` では共通部品を定義元から直接importします。従来のimport先からの再exportは、既存の開発スクリプト等の呼び出し元との互換性を保つために残します。新規コードはこの互換用exportを経由せず、定義元を参照します。ライブの連番選択・CSV追記と、タイムシフトの3ファイル排他確保・時刻順ソートは各レコーダーに残します。

タイムシフトのプレイリスト・鍵・初期化情報・メディア取得は `retryTimeshiftRequest` の再試行判定を共用します。最大4試行・500/1000/2000msの待機、通信エラーと408/429/5xxの再試行、待機中の停止を維持します。要求数・HTTPエラー・取得/再試行待機時間はセグメント取得側で計測します。ライブの認証更新・URL差し替え・再試行方針は変更しません。

AES-128-CBCのIV生成と復号は `core/nico/hls-crypto.ts` を共用します。鍵取得・キャッシュ・認証更新・暗号方式/鍵長の検証は各取得処理に残します。タイムシフトの不正IV拒否と、ライブの既存のIV解釈は変更しません。

視聴WebSocketのHLS応答解析と共有型は `core/nico/watch-protocol.ts` に置きます。`parseStreamMessage` の `live` 方針はCookieの省略値補完・プリミティブ値の文字列化・追加情報の取得を維持し、`timeshift` 方針は4項目が文字列のCookieだけ採用します。WebSocket接続・ping/keepSeat・タイマー・終了/再接続の判断は各セッションに残します。

2026-09-09の共通化では、既存のファイル名・CSV・録画ライフサイクルのテストを維持し、再試行待機の計測と停止、暗号文・IV解釈、Cookie補完と画質変換のライブ/タイムシフト差、および両WebSocketセッションへの結線を追加検証しました。全523テスト（Web Pushのローカル検証データを含む。clean worktreeでは3件少ない）、format・lint・typecheck・buildを通過。公開ライブ `lv351349754` を共通化の途中と完了後に30秒ずつ録画し、映像・音声保存、FFmpeg終了コード0、errorsなしを確認しました。この番組のコメントは0件で、実コメント受信の確認とはしていません。認証付き実タイムシフトの再取得は行っておらず、偽応答を使う既存の全編取得・停止・欠落・コメント保存テストで確認しています。

### 録画カードのプレビュー

FFmpeg 8.0.3を`--disable-x86asm`付きでビルドすると、x86の縮小処理でピンクや緑の画像になる既知の不具合があります（[上流の修正](https://github.com/FFmpeg/FFmpeg/commit/62285be0096319310d7012bbab1739db79926c4d)）。`scale`に`flags=bicubic+accurate_rnd`を指定し、問題のMMX処理経路を避けます。macOS上のx86版で同じ症状と回避策の有効性を確認しました。

`npm run ffmpeg:verify`は、合成した4色の640×360映像を配布用FFmpegと本番の画像生成関数で320×180へ縮小し、寸法と画素の色まで検証します。FFmpegは色が壊れていても終了コード0と正常なJPEGマーカーを返すため、それらだけでは十分ではありません。検証専用の開発依存`jpeg-js`でJPEGを独立にデコードし、macOS・Windowsのビルド後・パッケージ後の検証に使用します。

カード左側にプレビュー領域を追加したため、ライブ・タイムシフトともに配信者情報と録画統計を項目単位で折り返します。最小ウィンドウ幅760pxでも停止・ファイル表示ボタンを維持するための意図したレイアウト変更です。

カード内の画像は、取得済み・復号済みの映像セグメントから約5秒おきに作ります。ライブ・タイムシフトともに録画用パイプへ渡したデータを利用し、追加の放送接続や録画ファイルの読み直しはしません。保存成功の確認ではなく受信映像の確認です。音声再生はありません。タイムシフトでは取得中の位置を表示するため、放送時刻どおりには進みません。

`core/nico/video-sample.ts` の通知は受付だけを同期実行し、失敗を録画へ伝えません。`app/recording-preview.ts` は画面からの要求がある間だけ生成し、全番組で1プロセス・各番組5秒間隔に制限します。待ち行列は作らず、忙しい時は更新を飛ばします。更新が古く、直近15秒以内に映像が届いた番組に順番を譲り、同時到着で特定のカードだけが更新され続けることを防ぎます。入力は1セグメント16MiB・初期化情報1MiBまで、出力JPEGは256KiBまでです。入力サイズの上限でスキップした場合は、実際のサイズと上限を録画パートごとに一度だけdebugログへ残します。ライブの初期化情報は取得側で、その他の入力はプレビューの受付側で診断します。タブ切替・購読解除では診断済み状態を保持し、パート切替・録画終了で解放します。

`core/nico/preview-image.ts` は選んだセグメントと初期化情報だけをFFmpegへ渡し、キーフレーム以外のデコードを省いて最初の1枚を最大320×180に縮小します。デコード・フィルタ・エンコードはそれぞれ1スレッド、生成の上限は3秒です。キーフレームを含まない区間などで画像を作れなければ次の機会に再試行します。画像生成の失敗はdebugログだけに残します。FFmpegのstderrは末尾2KiBだけを保持し、失敗時に最後の2行と終了理由を添えます。

画像は専用IPCで取得し、通常のstatus配信・録画履歴・メタデータには含めません。画面内のカードだけが1秒おきに要求し、画像は更新時だけ返します。タブ移動、画面外へのスクロール、非表示、最小化、録画停止・再開時に購読を解放し、要求が3秒途絶えた場合も新たな生成を止めます。表示済みの画像はrendererのメモリに録画パートごとに1枚保持し、録画タブに戻った直後はその画像を暗く表示します。新しい画像が届いたら通常の明るさに戻します。非表示中の画像生成は再開せず、録画の終了・パート切替でキャッシュを解放します。最後の画像が15秒以上古い場合も、文字を重ねず画像を暗く表示します。画像とサンプルはメモリ内だけで扱い、プレビューファイルは作りません。

2026-09-09にmacOS arm64で、公開ライブ `lv351351054` の30秒録画（映像・音声・コメント、FFmpeg終了コード0、errorsなし）と隔離Electronでのプレビュー更新・タブ切替・非表示からの再開を確認しました。UI検証では表示用のログイン状態だけを差し替え、認証経路は使用していません。760px幅の表示も確認済みです。同放送の1280×720の1セグメントからの画像生成は、別プロセス起動込みで5回30〜40ms、JPEG約10KiBでした（この環境・映像での参考値）。Windowsと認証付き実タイムシフトは未確認で、両OSのパッケージ検証にJPEG生成を追加し、タイムシフトは偽応答による結線・復号・保存継続テストで確認しています。

### ログ

- ユーザーが見る情報 (検知、録画の開始・終了、エラー) は `info` 以上、内部の状態遷移は `debug` です。
- メインプロセスは `info` 以上と `debug` を別のリングバッファ (各 2000 件) で保持します。画面へは各バッファの直近1000件を渡し、ログタブの「debug を表示」で切り替えます。
- ファイル (`userData/logs/app.log`) と標準出力は `info` 以上を書きます。「debug を表示」が有効な間と開発時は `debug` も書きます。5 MB を超えると `app.log.1` に退避します。

### デスクトップ通知

`RecordingManager.notify` が録画開始と終了結果、空き容量不足への切り替わりで Electron の `Notification` を呼びます。自動・手動ライブ・タイムシフトで同じ `notificationsEnabled` 設定（既定true）を使い、無効または `Notification.isSupported()` がfalseなら送信しません。放送の検知だけでは通知せず、録画ジョブを開始した時点で通知します。開発モードを理由に抑止する分岐はありません。

macOSの通知にはアプリの署名が必要です。`npm run dev` で使う `node_modules/electron/dist/Electron.app` と、署名済みの配布アプリは別に確認します。2026-09-09にElectron 44.0.0の開発用実体で隔離した通知検証を行い、`isSupported()` はtrue、`show()` は正常復帰した後に `failed` イベントで `UNErrorDomain error 1` が返ることを確認しました。開発用実体は `adhoc,linker-signed` で、署名・OS側の通知許可が原因候補です。エラーだけから両者のどちらかに断定はしていません。仕様は [ElectronのNotification API](https://www.electronjs.org/docs/latest/api/notification) を参照してください。

現在の実装は同期例外を `notification failed` として記録しますが、非同期の `failed` イベントは購読していません。ログに失敗がないことや `isSupported()` がtrueであることだけでは、通知表示の成功を判断できません。自動テストは `show()` の呼び出しまでを確認し、OS上の表示は保証しません。表示の確認は署名済みアプリで、アプリの通知設定・OSの通知許可・集中モードも確認して行います。パッケージの署名手順は [mac-signing.md](mac-signing.md) を参照してください。

### 録画対象の並び替えと一括操作

- 録画対象タブのつまみの右にあるチェックは操作対象の選択、名前・ユーザー ID の後の「有効」は自動録画の設定です。無効な配信者も選択できます。ヘッダーで一覧全件を選択・解除でき、一部選択は中間状態で表示します。
- 左端のつまみをドラッグすると挿入位置を線で表示し、ドロップ時に順序を保存します。上下端に保持すると自動スクロールします。つまみにフォーカスして Alt + ↑ / ↓ でも移動できます。選択中でも移動するのはつまんだ 1 行だけです。
- 操作中は重複操作を止め、完了後に元の操作要素へフォーカスを戻します。削除した行は隣の選択欄へ戻します。利用者が別の要素へ移動していた場合は、そのフォーカスを優先します。追加中の行操作は従来どおり制限します。
- `settings.targets` の配列順を表示順として保持し、再起動後も復元します。新規追加は末尾、名前などの更新は元の位置を保ちます。`targets:move` は移動元と挿入先の ID だけを受け取り、最新の一覧を更新するため、同時に追加された行も失いません。順序変更だけでは放送検知を再起動しません。
- 選択は `useTargetSelection` がタブ内だけで保持します。設定の再取得では維持し、一覧から消えた対象は選択から外します。新規追加・取り消しで戻った対象は選択せず、タブを離れると全解除します。
- `SelectionToolbar` は選択件数・解除と操作ボタンの配置だけを担当します。将来の一括操作は呼び出し元でボタンと処理を追加し、操作ごとの確認や通信制限を適用します。
- 「有効化」「無効化」は選択した配信者の自動録画をまとめて切り替え、選択と並び順を保持します。全員が既に同じ状態なら該当ボタンを無効にします。保存・変更通知は 1 回にまとめ、保存失敗では全件を元の状態に保ちます。無効化しても進行中の録画は継続します。
- 一括削除はメイン側で件数を確認し、対象から外します。行ごとの削除は確認なしです。進行中の録画・録画ファイル・履歴は削除しません。有効な対象が 0 件になった場合は、従来どおり放送検知を止めます。
- 削除・取り消しはそれぞれ 1 回の設定保存と変更通知にまとめます。保存に失敗した場合はメモリ内の設定も変えません。復元には実際に削除した対象の名前・有効状態・追加日時を使い、同じ ID が再登録済みなら現在の登録を優先します。削除時の ID 順も保持し、取り消しでは元の後続行の前に戻します。削除後に残った行を並び替えていても、その順序は巻き戻しません。
- 削除後の通知の「取り消す」で一括復元できます。削除失敗時は選択を保持し、復元失敗時は通知の「再試行」からやり直せます。
- 手編集などで数字以外の ID が残っても、削除・無効化・並び替えは可能です。有効化は数字の ID だけを受け付けます。取り消しでは不正な ID を無効状態で復元し、不正・欠落した追加日時を復元時刻で補正します。復元データは `userId` / `name` / `enabled` / `addedAt` のみを保存します。
- 対象操作の応答では対象リストだけを更新します。状態通知に伴う設定取得も、取得開始後の対象操作や未保存のタブ・表示設定を巻き戻しません。

### 録画対象のフォロー確認

- 表の表示範囲に 200ms 留まった有効行だけを確認します。画面外の先読みはせず、タブ移動・ウィンドウ非表示中は新規取得を止めます。開始済みの通信は完了させ、結果をキャッシュします。
- 表示監視は有効な対象 ID の集合が変わったときに更新します。並び替えだけでは張り直さず、待機中の手動再確認も維持します。
- メイン側の `FollowStatusCache` が、対象追加も含めて同時 1 件・開始間隔 1 秒以上を守ります。メイン側に待機列を作らず、次に問い合わせ可能な時刻を画面へ返すため、画面外になった対象への送信は残りません。
- 成功結果は 5 分間再利用します。再取得に失敗しても前回の結果を保持し、画面では「前回：フォロー中」などと区別します。ログイン状態の変更・再ログイン時は画面とメイン両方の結果を破棄します。
- HTTP 429・5xx・通信例外ではフォロー確認全体を休止し、30 秒・60 秒・120 秒後に各 1 件を試します。`Retry-After` (秒数 / HTTP 日付) があればその時刻より早く再試行しません。3 回の再試行も失敗したら自動確認を止めます。手動の「再確認」でも残りの休止時間は守ります。
- 401・403 などの 4xx (429 を除く) や不正な応答形式は自動で再試行せず、対象ごとに手動再確認を待ちます。再確認は最低 30 秒空けます。休止はフォロー表示用 API だけに適用し、録画・放送検知には影響しません。
- 失敗理由・休止・復帰は `[follow]` の debug ログへ記録します。パッケージ版でファイルにも記録する場合は、事前にログタブの「debug を表示」を有効にしてください。

## CI とリリース

- PR と main への push で GitHub Actions (`.github/workflows/ci.yml`) が ubuntu と windows で format / lint / typecheck / test / build を実行します。macOS arm64 と Windows x64 では FFmpeg のビルドとパッケージ内実体の検証も行います。
- `v0.1.0` のような `v` 始まりのタグを push すると、macOS (Apple Silicon) と Windows (x64) のパッケージを作り、下書きのリリースに添付します (`release.yml`)。内容を確認してから公開してください。
- 本家の Release は macOS の署名・公証と、DMG / ZIP 展開後の Gatekeeper / FFmpeg 検証を必須にします。Windows は未署名の NSIS を作り、展開後の FFmpeg を検証します。手動実行ではリリースを作らず、検証済み成果物を Actions の artifact に保存します。必要な Secrets と検証手順は [mac-signing.md](mac-signing.md) を参照してください。

### 新しいバージョンの表示

- パッケージ版は起動時と 6 時間ごとに、GitHub Releases の最新の正式リリースを認証なしで確認します。設定タブの「情報」から手動確認もできます。開発起動では自動確認しません。
- 更新があれば画面上部にバージョンと「リリースページを開く」を表示します。ダウンロード・アプリの置き換えはユーザーが手動で行います。アプリからの自動インストール・再起動はありません。
- リポジトリが非公開、または正式リリースがなく API が 404 を返す場合は、「公開された更新情報を取得できません」と表示します。「更新なし」とは区別し、録画・検知は継続します。GitHub のトークンはアプリに持たせません。
- 通知先は `src/main/app/update-checker.ts` の `honishi/nico-live-recorder` に固定しています。fork から別のリポジトリのリリースを案内する場合は、この参照先も変更します。通知用メタデータファイルは不要です。配布時の署名・公証要件は上記のリリース手順に従います。
- 公開時は `package.json` のバージョンとタグ (`v0.2.0` など) を一致させ、その正式リリースを GitHub の Latest に指定してください。下書きとプレリリースは通知しません。バージョンは SemVer で比較します。
- 手動確認も最低 60 秒間隔に制限します。通信は 10 秒で中断し、API 制限時は最低 1 時間、解除時刻が先ならそこまで待ちます。通信失敗時も、既に検知した更新の案内は保持します。確認状態はメモリ内だけに保持します。
- 公開前の確認は `test/app/update-checker.test.ts` で API をモックします。公開後は旧バージョンのパッケージ版で、実リリースの通知とリンクを macOS / Windows それぞれで確認してください。

## パッケージング

```bash
npm run package:mac   # release/ に dmg / zip
npm run package:win   # release/ に nsis インストーラ
```

FFmpeg は公式ソースから LGPL-2.1-or-later の構成でビルドし、完全な対応ソースと許諾文を同梱します。パッケージ作成前に `npm run ffmpeg:build` を実行してください。macOS arm64 / Windows x64 それぞれのネイティブ環境で作成し、同梱した実体を `afterPack` で検証します。取得元、前提ツール、ライセンス条件、検証手順は [ffmpeg.md](ffmpeg.md) を参照してください。

### アプリアイコン

アプリアイコンは `build/icons/` のサイズ別 PNG、トレイアイコンは `resources/tray/` の PNG が元データです。出荷用の `build/icon.icns` と `build/icon.ico` は、1024px の 1 枚から縮小すると 16 / 32 / 64px で括弧が潰れるため、サイズ別に描き分けた `build/icons/*.png` から `npm run icons:build` (macOS 専用。`iconutil` を使う) で組み立て、生成物ごとリポジトリに含めます。アイコンを更新したときだけ実行してください。開発起動でも Dock / タスクバーに同じアイコンを出します。
