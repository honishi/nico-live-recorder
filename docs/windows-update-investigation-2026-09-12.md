# Windows 自動更新の調査・検証記録（2026-09-12）

Windows の試験用配布で発生した更新停止、その切り分け、既知対策の取り込み後の結果を記録します。今後の実施手順は [Windows 自動更新の試験手順](windows-update-testing.md) を参照してください。

## 最終的な判断

electron-builder 26.16.0 と更新ボタンの修正を含む 0.5.4 → 0.5.5 は、ユーザーの手操作で3回成功しました。うち2回はスナップショットを復元したクリーンな Windows で、現在のユーザーのみ／全ユーザー向けを各1回実施しています。最後の2試験では、ボタンの非活性・進行表示、約1分での更新・再起動、変更した設定の保持、全ユーザー向けの UAC 承認後の更新成功が報告されました。

ユーザーはこの結果をもって今回の Windows 試験を十分と判断し、本番への取り込みを進める方針としました。ただし、最初の停止の内部原因や、既知対策がその原因を解消したかは確定していません。対策前の同一配布物でも再試験は4回成功しています。

本記録時点で、本番 `main` への取り込みと、本番配布先での 0.5.2 → 0.5.3 の最終確認は未実施です。試験用と本番で同じバージョン番号を使う計画ですが、アプリの識別情報とリポジトリは別です。

## 初回停止で観測したこと

更新の検出、ダウンロード、通常終了では適用されないことを確認した後、UTC `2026-09-11T21:28:20.635Z` に更新を開始しました。プロセスの関係は次のとおりです。

```text
0.5.1 の更新インストーラー（PID 4684） --updated /S --force-run
  → old-uninstaller.exe（PID 4840） /S /KEEP_APP_DATA /currentuser --keep-shortcuts --updated ...
    → SysWOW64 の powershell.exe（PID 6296）
      Get-CimInstance Win32_Process とインストール先パスの照合
```

インストーラーの対象は x64 アプリですが、NSIS の実行ファイルは32bitです。コマンド上の System32 パスは WOW64 のリダイレクトを受け、実際には SysWOW64 の PowerShell が動いていました。

PID 6296 は数分後も残存し、累積 CPU 時間が `152.40625` 秒から `219.84375` 秒へ増えました。別に行った ARM64 PowerShell の同等照会はすぐ終了し、対象アプリのプロセス数は0でした。ただし、別プロセスでの成功は元のプロセスの内部状態を示しません。

イベントを後から照合すると、同じ PID に次の記録がありました。

| UTC              | イベント                              | 内容                     |
| ---------------- | ------------------------------------- | ------------------------ |
| 21:28:58.880     | Windows PowerShell 400                | EngineState が Available |
| 21:29:02.1266925 | Windows PowerShell 403、Record ID 381 | EngineState が Stopped   |

Stopped の後にも OS のプロセスが残って CPU を消費していました。したがって「CIM 照会がずっと返らなかった」とまでは断定できず、PowerShell ホストや関連リソースの終了処理も調査対象です。イベント403は照会成功やプロセス終了の証明にはなりません。

electron-builder 26.15.3 の `templates/nsis/include/allowOnlyOneInstallerInstance.nsh` の `FIND_PROCESS` は、子 PowerShell の終了を待つ実装で、外側の待機時間制限がありません。確認できた直接の停止構造は、この子プロセスの残存と NSIS の待機です。

7種のイベントログを比較しましたが、初回失敗の時間帯に原因を特定できる WMI・Defender のエラーは見つかりませんでした。これを OS や WMI に問題がなかった証明とは扱いません。元の停止中プロセスのダンプは採取しておらず、内部スタックによる原因特定はできていません。

復旧時は当該試験の3プロセスだけを終了しました。停止はアプリ本体の置き換え前で、0.5.0 が残り、手動起動と試験設定の保持を確認しました。「停止後に新版を手動上書きインストールして復旧する」経路を確認したわけではありません。

## 切り分けから得た知見

- アプリ・依存を変更せずに4回の再試験が成功しました。初回インストールやキャッシュの破損を原因とする証拠はありません。
- x86 PowerShell の単独照会は約6秒、ARM64 は約0.5〜0.7秒でした。`-NoProfile -NonInteractive` の有無を含む8回の試行はすべて終了し、元の数分単位の停止は再現しませんでした。調べた標準プロファイルも存在しませんでした。
- 復元後に独立した事前 CIM 照会を省いても更新は成功しました。ただし初回インストーラー自身が CIM を使うため、「CIM が未使用なら停止する／しない」という証明にはなりません。
- インストーラーは既存版のアンインストーラーを一時領域へコピーして実行します。更新先だけを新しいビルドツールで作っても、更新元に埋め込まれた処理は置き換わりません。
- ARM64 版のアプリを作るだけでは、32bit インストーラーと PowerShell の経路が変わるとは限りません。
- 更新対象アプリが終了した後の停止は、アプリ内タイマーでは救済できません。独自 NSIS の全面変更や、タイムアウトを「アプリ未起動」とみなして強行する対策は採用しませんでした。

26.16.0 は2026-09-02公開で、導入時に `.npmrc` の公開後7日ルールを満たしていました。26.16.1 は当時まだ7日未満だったため選びませんでした。取り込んだテンプレートでは対象の PowerShell 呼び出し4か所に `-NoProfile -NonInteractive` が付いていることを確認しました。これは対話するプロファイル等への対策で、CIM の置き換えや NSIS の待機タイムアウト追加ではありません。

ボタンの修正前から、メイン側は最初の受付で `installing` へ同期的に遷移し、追加の要求でインストーラーを重複起動しない構造でした。既存テストで一度だけの適用を確認しています。修正後は隔離した Electron で実際の React コンポーネントを表示し、受付前後の非活性維持、10回の追加クリックでも要求が1回だけであること、busy / not-ready / IPC エラー時の再操作、録画中の抑止を確認しました。

## 証拠の所在と再発時の方針

継続して追える資料は、上記の固定コミット、Actions 実行、試験用 Releases の配布物・`build-info.json`・ハッシュです。本書には原因判断に必要な観測を転記し、Git 管理外ファイルがなくても結論と限界を読めるようにしています。

元の生ログ・環境情報・設定比較・調査メモはローカルの `.cache/auto-update/` に保全しました。このディレクトリは Git 管理外で、別の checkout にはありません。次は証拠の識別用です。

| ローカルの保全物（`.cache/auto-update/` からの相対パス）       | SHA-256                                                            |
| -------------------------------------------------------------- | ------------------------------------------------------------------ |
| `snapshot-prep-2026-09-12/windows-evidence.zip`                | `0d24efe59e8d273bd95924befa718e781d65d3553f92652f31f3ed2082a84698` |
| `snapshot-retest-2026-09-12/evidence-1789169604392076000.zip`  | `0fabac8f11a6f1782c1d1082b3a9285e38e5586e3007a5654b4cf6fc4519072b` |
| `snapshot-retest2-2026-09-12/evidence-1789172700796370000.zip` | `10373d2fe56d95daa4b3b2be022825b703166ee695729af1b05e1c51842704f9` |

これらの ZIP はログ等の保全物であり、実障害のメモリダンプではありません。タスクマネージャーによるダンプ作成は、別途起動した待機用 PowerShell で手順だけ検証しました。

診断スクリプトは当時の版・変数・DLL・転送先に依存するため、本体の実行用スクリプトとして取り込みません。次に同様の停止が起きたら、[証拠採取の手順](windows-update-testing.md#停止したときに残すもの) に従い、対象を終了する前にダンプと親子関係を採取し、CIM 照会中なのか終了処理中なのかを絞り込みます。

今回の結果は Windows 11 ARM VM 上の確認です。通常の Windows x64 実機、本番配布先での最終更新、UAC 拒否後の復帰、実録画・履歴の更新前後保持など、今回個別に実測・報告されていない項目を確認済みにはしません。macOS のローカル署名付き更新試験は [開発文書の別記録](development.md#検証記録-2026-09-12) にあり、今回の Windows 試験と区別します。
