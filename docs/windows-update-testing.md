# Windows 自動更新の試験手順

Windows の配布版を使い、更新の検出・ダウンロード・置き換え・再起動を確認する手順です。GitHub Actions のビルド成功と、Windows のデスクトップでの更新成功は別に記録します。アプリの設計と通常のリリース手順は [開発者向けドキュメント](development.md#アプリの自動更新) を参照してください。

## 試験環境を分離する

試験用リポジトリに、更新元 A と更新先 B の2バージョンを配布します。A と B の識別情報は揃え、本番とは次の項目を分離します。

| 項目                   | 2026-09-12 の試験で使用した値                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| アプリID               | `com.honishi.nico-live-recorder.update-test`                                                                 |
| パッケージ名           | `nico-live-recorder-update-test`                                                                             |
| 製品名・実行ファイル名 | `NicoLiveRecorderUpdateTest`                                                                                 |
| 設定・履歴・ログ       | `%APPDATA%\nico-live-recorder-update-test`                                                                   |
| 更新キャッシュ         | `%LOCALAPPDATA%\nico-live-recorder-update-test-updater`                                                      |
| 録画の既定保存先       | Windows の「ビデオ」内の `NicoLiveRecorderUpdateTest`                                                        |
| 更新配信先             | [honishi/nico-live-recorder-update-test](https://github.com/honishi/nico-live-recorder-update-test/releases) |

`NLR_USER_DATA` だけでは electron-updater の更新キャッシュを分離できません。生成された `app-update.yml` の `updaterCacheDirName` も確認します。更新後の自動起動でも分離が維持されるよう、環境変数を指定せずに起動しても試験専用の既定パスを使う構成にします。設定画面で本番の録画保存先を選ばないでください。

全ユーザー向けにインストールしても、アプリの設定は実行したユーザーの userData に置かれます。インストール方式と、実際に起動・更新操作したユーザーを記録します。

## 試験用ビルドを作る

製品の変更を本体の作業ブランチへコミットしてから、試験用ブランチに取り込みます。試験専用の識別情報・配信先・ワークフローは本体へマージしません。

実装例は `test-auto-updates` の固定コミット [`c1038e6`](https://github.com/honishi/nico-live-recorder/tree/c1038e6fddc9b50508f8426801b98f4b16b583c3) にあります。

- [Windows 用の2バージョン生成ワークフロー](https://github.com/honishi/nico-live-recorder/blob/c1038e6fddc9b50508f8426801b98f4b16b583c3/.github/workflows/release.yml)
- [試験アプリのパッケージ設定](https://github.com/honishi/nico-live-recorder/blob/c1038e6fddc9b50508f8426801b98f4b16b583c3/electron-builder.yml)
- [パッケージ作成時のアプリID確認](https://github.com/honishi/nico-live-recorder/blob/c1038e6fddc9b50508f8426801b98f4b16b583c3/scripts/ffmpeg/after-pack.cjs)
- [NSIS 展開後のアプリ・更新情報の検証](https://github.com/honishi/nico-live-recorder/blob/c1038e6fddc9b50508f8426801b98f4b16b583c3/scripts/ffmpeg/verify-artifacts.mjs)

この例は 0.5.4 / 0.5.5 を生成します。再利用時は未使用のバージョンへ変更し、workflow 内の対象版・成果物名・保存先を揃えてください。既存のタグや配布ファイルを差し替えず、過去の試験を追跡できる状態を保ちます。

1. 依存のロックファイルを維持し、format・lint・typecheck・test を通します。
2. 同じ Windows ジョブで FFmpeg を1回ビルドし、同じアプリソースから A / B を作成します。ランナー内で `npm version ... --no-git-tag-version --ignore-scripts` を使い、B の版だけを変更します。
3. `electron-builder --win --x64 --publish never` で生成します。版ごとに検証・退避し、生成物が次の版に混ざらないようにします。
4. NSIS を実行せずに展開し、アプリ名・バージョン・更新配信先・キャッシュ名、同梱 FFmpeg の実行を検証します。ASAR 内のパスも、Windows では `path.join` で組み立てます。
5. `.exe`、`.exe.blockmap`、`latest.yml`、ソースコミットと Actions 実行IDを含む `build-info.json` を版ごとに保存します。
6. ダウンロード後にメタデータの版・ファイルサイズ・SHA-512、ビルド元を照合します。Release 添付後は各ファイルのサイズ・SHA-256 もローカルの検証済み成果物と照合します。

試験用ワークフローを確認・更新した後の実行例です。ブランチ名を指定し忘れると、本体向けのビルドになるため注意してください。

```sh
gh workflow run release.yml --ref test-auto-updates --repo honishi/nico-live-recorder
```

例の Actions artifact の保持期間は14日です。長期の追跡には公開 Release の添付ファイル、ソースコミット、実行URL、ハッシュを使います。ログも必要なら期限前に保全します。

## 公開順と更新元の選び方

このアプリは正式版を取得し、下書き・プレリリース・ダウングレードを対象にしません。試験用リポジトリでも B は正式版・Latest として公開し、公開された `latest.yml` が B を指すことを確認します。

A のインストールを確認してから B を公開すると、検出前から順に観察できます。両版を先に公開しても試験は可能ですが、その場合も最初に A を手動インストールします。Release 一覧の Latest は B なので、取り違えないよう A のリンクを明記します。

更新開始時の UI は A のコードです。ボタンの修正を B だけに入れても、押下時の表示は確認できません。また NSIS 更新では A が持つ旧アンインストーラーも動くため、electron-builder の対策を確認する際は A / B の両方を対策入りのツールで作ります。

既に旧ツール製の更新対応版を一般配布している場合は、そこから対策版への移行も別途確認します。初めて自動更新を一般公開する場合は、対策入り A → B を基本経路とし、自動更新機能のない公開版から A への移行は手動上書き更新として扱います。

## Windows で手動操作する

普段の利用者と同じ方法で、インストーラー・ショートカット・画面のボタンを操作します。通常の受け入れ試験では、PowerShell からのアプリ起動やプロセス監視を併用せず、診断を行う試験とは記録を分けます。

VM 内に Node.js やビルド環境は不要です。Windows 11 ARM の VM で x64 ビルドを使う場合はエミュレーションになるため、通常の Windows x64 実機と区別して記録します。

1. 試験用アプリが未インストールの状態を用意し、OS ビルド・CPU アーキテクチャ・起動方法を記録します。
2. A を「現在のユーザーのみ」でインストールします。起動後の版、試験用保存先を確認し、設定を1つ変更して比較用に控えます。
3. B の公開後、ショートカットから起動するか設定画面で更新を確認します。手動確認には最低60秒の間隔があるため、短時間の連打で再確認させようとしません。
4. B のダウンロード完了後、トレイから通常終了して起動し直します。A のままであり、通常終了では更新されないことを確認します。
5. 「再起動して更新」を押します。直後から非活性になり「更新を開始しています…」が表示され、受付後も操作可能に戻らないことを確認します。
6. 更新開始から再起動までの所要時間、起動後の B の版、設定保持を確認します。試験用ログと、用意した録画・履歴がある場合はその保持も確認します。
7. 別のクリーンな状態から「このパソコンを使っているユーザー全員」で同じ試験を行います。UAC の表示有無と、承認後に更新・再起動できたかを記録します。

録画中の更新抑止や、UAC 拒否後の手動復帰は追加の確認項目です。成功経路の試験だけで確認済みにはしません。ニコニコへのログインが必要な録画・検知経路は人間が確認します。

スナップショットを復元する前には、ログ・設定比較・環境情報などを VM の外へ退避します。復元は OS 更新状態も戻すため、復元前後の OS と PowerShell のバージョンを記録します。「クリーン」は試験アプリ・その設定・更新キャッシュの有無で定義し、OS が一度も CIM を使っていないことまでは意味しません。

## 停止したときに残すもの

約1分かかる成功例があるため、数秒無反応なだけで失敗と判定しません。長時間戻らない場合は、時刻と画面を記録し、終了・再起動・スナップショット復元の前に次を保存します。

- ソースコミット、Actions 実行ID、A / B の版とファイルハッシュ、インストール方式。
- OS・PowerShell の版、CPU アーキテクチャ、VM の場合は仮想化ソフトと復元条件。
- アプリログ、設定の比較結果、更新インストーラー・旧アンインストーラー・子 PowerShell の PID、開始時刻、実行パス、親子関係、CPU 時間の推移。
- 該当時間帯の Application / System / Windows PowerShell / PowerShell Operational / WMI-Activity / Windows Defender / WindowsUpdateClient のイベント。時刻は UTC を併記し、イベントIDだけでなく Message・XML も保持。
- 再発時に対象を特定できれば、終了させる前のメモリダンプ。タスクマネージャーの「詳細」から対象 PID を確認して採取し、PID と時刻を付けて退避。可能なら時間をあけて2つ採取。

診断でプロセス列挙に CIM を使うと、調べたい処理を事前に動かしてしまいます。条件を分けたい場合は Toolhelp32 などによる親子関係の取得を検討し、監視方法も記録します。イベント上の PowerShell エンジン終了だけで、OS のプロセスも終了したとは判断しません。

過去の PID を使い回したり、PowerShell をまとめて終了したりしません。復旧操作の前に、今回の更新に属するプロセスかを開始時刻・パス・親子関係で確認します。ログ・ダンプには設定や認証情報が含まれる可能性があるため、Git や公開 Issue へ生データをそのまま添付せず、必要な部分を確認・加工します。

アプリ終了後にインストーラー側で止まった場合、アプリ内の120秒タイマーでは救済できません。アプリの完全終了や Windows 再起動後に、同じインストール方式・場所へ公式インストーラーで上書きする方法を復旧候補にします。ただし、手動更新も旧アンインストーラーを通るため、停止を必ず回避できるとは限りません。復旧できた場合も、更新試験の成功と区別して記録します。本番の設定・録画は削除しません。

## 結果の記録項目

各試験は、実施者（エージェントの実測／ユーザー報告）、日時、環境、版とハッシュ、クリーン状態の定義、インストール方式、操作方法、成功・停止・復旧、所要時間、設定・録画・履歴、ボタン表示、UAC の結果を記録します。未確認の項目は未確認のまま残します。

成功回数だけから発生率を推定せず、OS 版・監視条件・インストール方式が違う結果を同一条件の反復として扱わないでください。
