# Windows 自動更新の実機試験

`test-auto-updates` は、`add-auto-updates` (`23a09aa`) から派生した試験専用ブランチです。electron-builder 26.16.0 と更新ボタン配置・クリック後の非活性維持の修正を取り込んでいます。アプリの更新処理は共通で、識別情報・保存先・配信先とビルド手順を試験用に変更しています。試験用の設定一式は本体ブランチへマージせず、必要な不具合修正だけを戻します。

## 試験版の識別と保存先

| 項目               | 試験版                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------ |
| アプリ名           | `NicoLiveRecorderUpdateTest`                                                                                 |
| アプリID           | `com.honishi.nico-live-recorder.update-test`                                                                 |
| 設定・履歴・ログ   | `%APPDATA%\nico-live-recorder-update-test`                                                                   |
| 更新キャッシュ     | `%LOCALAPPDATA%\nico-live-recorder-update-test-updater`                                                      |
| 録画の既定保存先   | Windowsの「ビデオ」内の `NicoLiveRecorderUpdateTest`                                                         |
| 更新配信先         | [honishi/nico-live-recorder-update-test](https://github.com/honishi/nico-live-recorder-update-test/releases) |
| 試験するバージョン | 0.5.4 → 0.5.5                                                                                                |

旧版・新版で上記の識別情報は同じです。`NLR_USER_DATA` / `NLR_OUTPUT_DIR` の指定なしでも本番の保存先と分かれ、インストーラーによる再起動後も試験用の設定を使います。設定画面から本番の録画保存先へ変更しないでください。

Windows 11 ARMのVMではx64アプリのエミュレーションを使います。NSISの更新処理を試せますが、Intel/AMDのWindows実機を網羅した確認にはなりません。今回はmacOS版をビルドしません。

## ビルドと配信

本体リポジトリの既存の `release.yml` を、このブランチを指定して手動実行します。

```sh
gh workflow run release.yml --ref test-auto-updates --repo honishi/nico-live-recorder
```

Windowsランナー上でチェックとFFmpegビルドを行い、同じコード・同じFFmpegから2バージョンを作ります。更新先への版の変更はランナー内だけで行い、Gitのタグは作りません。各版のNSISを展開し、FFmpeg、更新情報のSHA-512・サイズ、配信先・キャッシュ名、アプリ名・版を検証してから成果物を保存します。

成果物は `windows-update-test-0.5.4` と `windows-update-test-0.5.5` で、保持期間は14日です。それぞれに `.exe`、`.exe.blockmap`、`latest.yml` と、ソースコミット・Actions実行IDを記録した `build-info.json` が入ります。

検証済み成果物は、テスト配布用リポジトリの `v0.5.4` / `v0.5.5` Releasesに、バージョンごとに分けて配置します。`v0.5.5` を正式版・Latestとして公開することで、テスト版0.5.4から検出できます。このアプリはプレリリースを取得しないため、試験用リポジトリでもPre-releaseにはしません。Actionsは成果物保存までを行い、Release公開は別途行います。今回はユーザーの指定により両版を公開し、0.5.5をLatestにします。既存のReleaseは上書きしません。

## 最初の動作確認

ユーザーがインストーラーとショートカットを手で操作して確認します。PowerShellからのアプリ起動や、診断用の監視処理は使いません。

1. Windowsへサインインし、GitHubからファイルを取得できることを確認します。VM内に開発環境は不要です。
2. ビルド成果物（または公開後の `v0.5.4`）の `NicoLiveRecorderUpdateTest-0.5.4-x64.exe` を実行します。最初は「現在のユーザーのみ」を選び、試験用アプリとしてインストールします。
3. アプリのバージョンが0.5.4、設定・保存先が上の試験用パスになっていることを確認します。設定を1つ変更し、更新後に比較できるよう値を控えます。
4. 0.5.5は公開済みの状態で試験します。ショートカットから通常起動するか、設定画面から更新を確認します。0.5.5がダウンロード済みになった状態で、トレイから通常終了して再び起動します。バージョンは0.5.4のままであることを確認します。
5. 「再起動して更新」を押し、直後からボタンが非活性になり「更新を開始しています…」が表示されることを確認します。受付後もボタンが押せる状態に戻らず、アプリが終了・更新・再起動することを確認します。
6. バージョンが0.5.5で、変更した設定が残っていることを確認します。試験用の `logs\app.log` に適用直前のログが残り、本番の設定・録画フォルダーを使用していないことも確認します。

試験用の録画を用意できたら、録画中の更新抑止と、更新前後の `recording-history.json` の保持も確認します。自動検知まで確認する場合は、ユーザーによるニコニコへのログインが必要です。

全ユーザー向けインストールでのUAC承認・拒否は追加試験です。拒否後にアプリが再起動しない場合は、手動起動して監視の再開を確認します。Windows版は未署名であり、初回インストールや更新がOSの保護機能に止められる場合は、その画面・結果も試験記録に残します。

## 再試験と記録

更新後に0.5.4へ戻して試す場合は、試験版だけをアンインストールし、旧版を再インストールします。ダウングレードは自動では行われません。キャッシュや設定を初期化する場合も、上表の試験用ディレクトリだけを対象にし、録画がないことを先に確認します。本番の保存先は削除しません。

記録には `build-info.json`、Windowsのバージョン・ARM/x64、インストール方式、更新前後の版、設定・履歴・ログの確認結果を含めます。ビルドの成功と、VM内での実更新の成功は分けて記録します。

## 2026-09-12 の手動試験結果（0.5.2 → 0.5.3）

ユーザーから、Windows VM で通常の手操作による 0.5.2 → 0.5.3 の自動更新に成功したと報告がありました。更新ボタンの押下後に非活性が維持されないように見えるという指摘を受け、0.5.4 / 0.5.5 に表示の修正を含めます。

この報告だけで以前の停止原因の解消や発生頻度を確定することはできません。0.5.4 → 0.5.5 の実更新とボタン表示は、公開後にユーザーが確認します。

## 2026-09-12 のVM試験結果

VMware Fusion上のWindows 11 ARM (OSビルド `10.0.26200.9445`) で、x64版を現在のユーザーのみにインストールしました。結果は **更新のダウンロードまで成功、適用は停止** です。

| 確認内容                      | 結果                                                                        |
| ----------------------------- | --------------------------------------------------------------------------- |
| 0.5.0の取得と初回インストール | 成功。VM内のSHA-256も配布物と一致                                           |
| 設定・ログ・録画先の分離      | 試験用パスを画面と設定ファイルで確認                                        |
| 0.5.1の自動検出・ダウンロード | 成功。「更新を準備しました」と表示                                          |
| ダウンロード後の通常終了      | 再起動後も0.5.0で、自動適用されない                                         |
| 通常終了後の設定保持          | 空き容量警告を5GBから4GBへ変更し、保持を確認                                |
| 「再起動して更新」            | アプリが終了し、0.5.1のNSISと旧版アンインストーラーが起動。その後停止       |
| 適用直前のログ保存            | `2026-09-11T21:28:20.635Z INFO 再起動して更新を適用します` をファイルで確認 |
| 中断後の復旧                  | 試験プロセスを終了後、0.5.0を手動起動可能。設定4GB・試験用録画先も保持      |

停止箇所は、electron-builder 26.15.3が生成した旧版アンインストーラーのプロセス確認処理でした。プロセスの親子関係と起動引数から、次の順序を確認しています。

```text
NicoLiveRecorderUpdateTest-0.5.1-x64.exe --updated /S --force-run
  → old-uninstaller.exe /S /KEEP_APP_DATA /currentuser --keep-shortcuts --updated ...
    → SysWOW64\WindowsPowerShell\v1.0\powershell.exe
      Get-CimInstance Win32_Process とインストール先パスの照合
```

子PowerShellは約4分後も実行中で、累積CPU時間が約152秒から約220秒へ増加しました。通常のPowerShellから行った同等の確認はすぐに終了し、該当アプリのプロセス数は0でした。実装上の対応箇所はelectron-builderの `templates/nsis/include/allowOnlyOneInstallerInstance.nsh` の `FIND_PROCESS` マクロです。32bit PowerShellとARMの組合せが関係する可能性がありますが、原因の確定やx64実機での比較は未実施です。

復旧時は今回のインストーラー・旧版アンインストーラー・その子PowerShellだけを終了しました。旧版の実行ファイルは0.5.0のままで、本番のアプリ・設定・録画先は操作していません。

0.5.1への置き換え・自動再起動・更新成功後の設定保持は未達です。録画中の更新抑止、実録画履歴の保持、全ユーザー向けインストールのUAC承認・拒否も今回の試験では未検証です。現行の配布物をWindows更新成功の根拠には使えません。

再試験ではインストーラーのプロセス確認処理を見直し、旧版と新版の両方を作り直す必要があります。旧版側に埋め込まれたアンインストーラーが停止箇所なので、新版だけの修正ではこの試験経路を解消できません。
